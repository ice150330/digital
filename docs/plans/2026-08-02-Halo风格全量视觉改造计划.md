## 1. 背景与目标

当前前端已经完成一轮基于 `pen/ui.pen` 的浅色分析工作台重构，但 `/screen` 仍是一个独立于工作台框架的全屏暗色大屏：

- `frontend/src/router/index.ts` 中 `/screen` 带 `meta.fullscreen: true`。
- `frontend/src/App.vue` 根据 `meta.fullscreen` 让 `/screen` 绕过 `AppLayout`。
- `frontend/src/views/ScreenView.vue` 直接导入 `styles/screen.css`，并使用 `data-theme="screen"`。
- `frontend/src/utils/chartTheme.ts` 存在 `ChartTheme = 'default' | 'screen'`，大屏走独立暗色色板和轴系。
- `DESIGN.md` 明确把 `/screen` 写成“唯一暗色例外”和“全屏暗色作用域”。

本次改造目标是把项目整体改成更强的 Halo 风格浅色现代工作台：

1. **默认主题统一为浅色系**：删除“暗色大屏例外”的视觉定位，所有页面基于浅色 Halo 语言。
2. **大屏并入整体页面框架**：`/screen` 不再绕过 `AppLayout`，侧栏、顶部状态、运行时信息与返回路径保持一致。
3. **大屏中心化重构**：从多块均匀图表改成“一个重点的唬人大图表放中心，围一圈小图标”的视觉结构。
4. **`ui.pen` 全量重构为圆角卡片现代设计**：读取 `pencil-halo.pen` 的设计语言，重建 `ui.pen` 的设计令牌、组件库、页面样张和大屏样张。
5. **不破坏数据与学术口径**：所有数字继续来自后端 API/产物；大屏强调“相关关系与模型行为”，不暗示因果收益。

## 2. Halo 设计语言提炼

从 `pen/pencil-halo.pen` 当前可读信息提炼本次视觉方向：

| 维度 | Halo 线索 | 本项目落地 |
|------|-----------|------------|
| 主题 | Light/Dark 双主题，但浅色变量完整 | 本项目默认只落浅色；暗色不作为 `/screen` 特例 |
| 主色 | `--primary = #5749F4` 紫蓝 | 替换当前偏蓝 `#3B82F6` 为更有记忆点的紫蓝主色 |
| 背景 | `--background/#FFFFFF`，`--tile/#F5F5F5` | 页面白底或极浅灰底，卡片白底，次级块用 tile |
| 文本 | `--foreground = #2A2933`，muted `#616167` | 标题更深、更柔和，正文不再偏冷蓝灰 |
| 边框 | `--border = #C5C5CB`，sidebar border `#D9D9DB` | 卡片用轻边框，不靠重阴影堆层次 |
| 圆角 | `--radius-xs = 6`，`--radius-m = 24`，`--radius-l = 40`，`--radius-pill = 999` | 控件小圆角，卡片 24，大视觉容器 40，胶囊 999 |
| 组件气质 | 大圆角卡片、胶囊导航、柔和 tile、干净数据表 | 从“冷静数据后台”升级为“现代圆角分析工作台” |

设计约束：虽然需要“唬人”，但不得使用无数据意义的装饰性光球、全屏暗色科技风、伪 3D 饼图或假动效数字。

## 3. 方案概述

采用“设计契约先行 → Pencil 视觉真相 → 前端令牌和大屏结构 → 全站圆角化 → 真实浏览器验收”的路线。

核心方案：

- `/screen` 保留路由，但取消 fullscreen 分支，成为 AppLayout 下的重点页面。
- 大屏主体改为 **中央转化星图**：中心是 ECharts 径向关系图，展示转化预测主线；周围一圈图标徽章展示样本、转化率、PR-AUC、默认 run、Top SHAP、分群、规则、预算模拟、Agent runtime 等状态。
- 全站视觉令牌改成 Halo 浅色体系：紫蓝主色、大圆角卡片、白底/tile 分层、柔和边框与轻阴影。
- `pen/ui.pen` 重构为新的视觉真相：保留设计系统、组件库、十路由样张，但全部改成 Halo 风格；重点新增 `/screen` v2 大屏样张。

不选方案：

- 不继续保留独立暗色 `/screen`：这与“默认浅色系”和“页面不再与整体框架分开”冲突。
- 不做纯营销页 hero：本项目是分析系统，不是落地页。
- 不新增后端算法主线：视觉重构不改变 ML 指标、双轨存储、Agent/Pi 协议。

## 5. 中央大屏方案

### 5.1 页面结构

`/screen` 在 AppLayout 内容区内展示，建议页面结构：

```text
AppLayout
  └─ PageHeaderBar：总览大屏 · Halo 版
      ├─ 顶部状态条：API 健康 / run_id / runtime / 数据口径
      └─ ScreenCanvas
          ├─ 中央转化星图（主视觉，占 55%–65% 首屏面积）
          ├─ 环绕图标徽章环（8–12 个小图标）
          ├─ 右侧洞察胶囊列（Top 3 结论、免责声明）
          └─ 底部微型指标带（实验矩阵、SHAP、预算模拟摘要）
```

### 5.2 中央转化星图

主图命名：**转化星图** 或 **Conversion Orbit**。

推荐技术：ECharts `graph` circular/radial 布局，必要时新增 `GraphChart` 按需注册。

数据来源全部复用现有接口：

| 星图元素 | 数据来源 | 含义 |
|----------|----------|------|
| 中心节点 | `/health` + `/models/metrics` | 默认 run、模型状态、PR-AUC |
| 渠道节点 | `/data/overview` | 各渠道转化率与样本规模 |
| 活动类型节点 | `/data/cross-matrix` | 渠道×类型热点 |
| 特征节点 | `/explain/global` | Top SHAP 特征 |
| 分群节点 | `/segments` | 主要簇规模与事后转化率 |
| 预算节点 | `/simulate/budget` 默认参数结果或既有摘要 | 推荐 K 与期望值口径 |

展示原则：

- 节点大小表达规模或重要性，颜色表达类别，不表达因果强弱。
- 连线宽度表达描述性转化率、lift 或 mean |SHAP| 的相对强弱，tooltip 写清字段口径。
- 中心节点显示 `PR-AUC`、`default_run_id`、`threshold`，但不把 Accuracy 当主指标。
- 图标题和页脚固定出现“相关非因果 / 模型行为”说明。

### 5.3 环绕小图标

环绕徽章不是一圈小图表，而是一圈可扫读状态图标：

| 图标 | 展示 | 数据源 |
|------|------|--------|
| 数据规模 | 样本量 | `/data/dashboard`.kpis |
| 转化占比 | 正类占比 | `/data/dashboard`.kpis |
| 渠道 | 最优渠道或渠道数 | `/data/overview` |
| 质量 | 质量问题条数 | `/data/overview` 或质量接口 |
| 模型 | PR-AUC | `/models/metrics` |
| 解释 | Top SHAP 特征名 | `/explain/global` |
| 分群 | 主簇名称/数量 | `/segments` |
| 规则 | Top lift | `/rules` |
| 预算 | 推荐 K | `/simulate/budget` |
| Agent | runtime/pi_fallback | `/agent/pi/status` |

视觉要求：

- 图标统一走现有 Iconify/Unicons 或升级后的图标封装。
- 徽章使用 Halo 胶囊或圆形 tile：白底、轻边框、主色 icon、短数字。
- hover 显示 tooltip；点击可跳转到对应路由。
- 1366×768 下不得溢出；窄屏降级为 2 行 icon strip。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 大圆角与现有密集表格冲突 | 表格显得臃肿 | 页面容器大圆角，表格行保持紧凑；避免每行都做大卡片 |
| 中央星图看起来炫但误导因果 | 学术诚信风险 | 标题、tooltip、页脚统一写“相关/模型行为”；不写“导致/提升收益” |
| 去掉 fullscreen 后 `/screen` 首屏空间变小 | 大图压缩 | AppLayout 下为大屏页面增加宽屏内容模式，中心图高度自适应 |
| `screen` 主题分支清理牵连图表 | 构建或视觉回归 | 先改类型与编译错误，再逐图验证；保留默认色板回退 |
| `ui.pen` 重构量大 | 容易只改新画布不改旧组件 | 以节点清单验收：Foundations、组件库、十路由样张都必须完成 |
| 当前工作树已有大量未提交改动 | 容易覆盖他人工作 | 执行前先确认改动归属；只改计划范围内文件，分阶段 diff 自查 |

## 10. 执行顺序建议

1. 先改文档契约和 `ui.pen`，确保“要长什么样”已经固定。
2. 再改 token 和全局组件，避免页面各自硬改。
